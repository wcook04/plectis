\begin{abstract}
Some software cannot be published. It may hold personal records, access keys, or
unfinished work. Its author can still describe it, but a description is only
testimony: a reader who doubts it has nothing to examine.

The usual remedy is to publish some tests. That is weaker than it looks. A test
that passes tells a stranger that a program repeated itself. It does not say who
chose the input, where the expected answer came from, whether the rule that
declared the pass tests the sentence it stands under, or how far the result may
be carried.

This paper describes Plectis, a public repository in which each of
\componentcount{} published claims carries a record naming seven things: the
exact version under test, the input, the procedure, the source of the expected
answer, the rule that decides a pass, the cases the claim declines to cover, and
the strongest conclusion the result supports. I call this a
claim--evidence--limit record. Its purpose is not to show that the private
system is good. It is to give a stranger an address for disagreement: a reader
who doubts a published claim can say which of the seven parts they reject,
rather than argue with prose about software they cannot see.

Then I audit the collection against its own standard, and report what that
found. Running every registered component once, \passcount{} pass,
\blockedcount{} stop at a declared boundary, and \errorcount{} fail with
unhandled errors rather than the declared refusals the contract requires. The
project's own verification floor is green --- \floorpasscount{} tests pass, none
fail --- and covers none of those \errorcount{}. Reading published descriptions
against the rules that enforce them finds cases where the description is the
stronger of the two, including one where prose promising to check
\emph{behaviour} is implemented as a search for fixed strings in a file that is
never executed.

The limits are structural, and they are the point rather than an apology. I
chose every published fragment, input, expected answer and rule; no independent
evaluator has examined the collection; and nothing here shows that the private
system works.
\end{abstract}

\section*{What this paper does not establish}
\addcontentsline{toc}{section}{What this paper does not establish}

Seven limits bound everything below. Each is stated once, here.

\begin{list}{}{\leftmargin 1.6em \itemindent -1.6em \itemsep 0.28em \parsep 0pt \topsep 0.35em}
\small
\item[] \textbf{L1 Origin.} Nothing a public repository does can show where its contents came from. I report that the published material was copied or adapted from the private system. That is testimony, and no argument here depends on it.
\item[] \textbf{L2 Correctness.} A run matching its stored record shows the same code produced the same answer again. It does not show the answer is right: in almost every case the expected answer and the code come from one hand.
\item[] \textbf{L3 Meaning.} A pass is a verdict on the rule that was written down, and that rule can be narrower than the sentence it stands under. Section~\ref{sec:audit} measures how often.
\item[] \textbf{L4 Reach.} The published parts are a selection I made from a system no reader can see. No result about one component carries to another, and none carries to the private whole.
\item[] \textbf{L5 Risk.} The publication checks reduce specific risks. A scan that finds nothing shows the scanner did not find the patterns it was designed to find, and nothing stronger.
\item[] \textbf{L6 Author control.} I chose every published fragment, input, expected answer, rule and limit --- including the method of Section~\ref{sec:audit} and the faults it looks for. No outside evaluation report is cited or included anywhere, and I know of none --- though that is a claim about my knowledge, not about the world: someone could have rerun this privately and never said so.
\item[] \textbf{L7 Inventory.} \componentcount{} is a count of registered claims, not a score. Even the unit of counting is a choice I control: one mechanism could have been registered as several components, or several as one.
\end{list}

\section{The problem}
\label{sec:problem}

I have a private software system I cannot responsibly publish: it holds personal
records, access keys, live browser and account information, working notes, and
unfinished tools. I would still like strangers to be able to test some claims
about it rather than accept my say-so.

Publishing a test looks like the answer and mostly is not. Suppose I write that
a component ``checks the recording hotkey behaviour'', publish a test, and the
test passes. A reader has learned that some program returned the value some
other program expected. They have not learned who chose the example, where the
expected answer came from, or whether the rule that declared the pass has
anything to do with hotkeys. Section~\ref{sec:audit} shows that this is not a
hypothetical: in the case just described, the rule searches an unexecuted file
for fixed strings.

So the question is not whether public tests are possible. It is what a public
test has to carry before a stranger can tell what it is worth.

This is a descriptive analysis of one repository, not a statistical study.
Runeson and H\"ost distinguish a case from the units of analysis within it
\cite[\S2.5]{runeson2009}; I borrow only those two terms. The named repository
version is the single case, and each component is one unit examined inside it.
No subset is used to estimate performance or to represent the private system.

\subsection{Threat model}
\label{sec:threat}

The adversary in this paper is the author. Not because I intend to mislead, but
because the privacy constraint hands one person every consequential choice, and
a structure that only works when its author is careful is not a structure.

At the audited version I choose: which private mechanisms are candidates; which
are published; how finely each is divided, and so what the count counts; which
evidence route each takes; the inputs; the expected values; what each validator
checks; where each refusal boundary sits; which group each entry is filed under;
which failures this paper explains, and in what tone.

That concentration permits a failure mode requiring no false statement anywhere.
Select the mechanisms that show well. Divide the favourable ones finely. Narrow
each claim until its fixed cases satisfy it. Give awkward material the least
demanding check. Declare as refusals whatever would otherwise fail. File small
replays under weighty names. Then let counts, categories, and the machinery of
records accumulate into an impression of scale that no individual sentence
asserts. A document can be cautious sentence by sentence while its arrangement
overstates, because a reader's impression forms on what is counted, named,
worked through, and left out.

\begin{center}
\small
\begin{tabular}{@{}>{\raggedright\arraybackslash}p{0.30\linewidth}>{\raggedright\arraybackslash}p{0.31\linewidth}>{\raggedright\arraybackslash}p{0.33\linewidth}@{}}
\toprule
\textbf{Author capability} & \textbf{What the record defends} & \textbf{What it does not} \\
\midrule
Choose which mechanisms are published & Nothing & The pool stays invisible (L4) \\
Choose the fixed inputs & The inputs are named and replaceable & I chose them (L4) \\
Supply the expected answer & Its source is a declared field, so a reader sees when it is mine & Declaring the source does not make it independent (L2) \\
Write a rule narrower than the claim & Rule and prose are separately readable, so the gap is findable --- Section~\ref{sec:audit} finds it & Finding it needs a reader; nothing detects it automatically (L3) \\
Draw a refusal boundary after meeting an awkward case & A pinned version fixes what was declared when & The record cannot show what was known before it (L6) \\
Repair a failure quietly & Receipts are append-only; the appendix keeps failures at the pinned version & Nothing forces me to run the case that would fail \\
\bottomrule
\end{tabular}
\end{center}

Selection also acts at two levels that are worth separating, because a reader can
defeat one and not the other. Within a component, the fixed input covers a few
cases out of many. Across the collection, the published components are my
selection from a private whole. An objection to the first can be settled by
changing an input; an objection to the second cannot be settled from the public
side at all.

There is also a tilt no reader can inspect. A private mechanism is easiest to
publish when it separates into a small task, returns the same output for the same
input, and runs in isolation. A collection built this way over-represents pure
calculation, replay, and record-checking, and under-represents stateful,
entangled, long-running behaviour --- before any question of honesty arises.

This paper is inside its own arrangement. Declaring the risk does not discharge
it, and nothing in the text can establish that the text is not doing what the
paragraph above describes. What can be done is to move the argument onto ground
where a reader does not have to believe me: fixed inputs they can change,
rules they can read, and, in Sections~\ref{sec:collection}
and~\ref{sec:audit}, measurements whose commands are published and whose results
are unflattering.

\section{The record}
\label{sec:record}

A component is one registered, runnable part of the project. Every entry in the
registry is required to carry the same seven things.

\begin{center}
\small
\begin{tabular}{@{}r>{\raggedright\arraybackslash}p{0.21\linewidth}>{\raggedright\arraybackslash}p{0.31\linewidth}>{\raggedright\arraybackslash}p{0.34\linewidth}@{}}
\toprule
& \textbf{Field} & \textbf{What it holds} & \textbf{What rejecting it means} \\
\midrule
1 & Subject and version & The exact commit under test & ``You are not testing what you say you are'' \\
2 & Input & A fixed sample, stored in the repository & ``Your example is not representative'' \\
3 & Procedure & One command a stranger can run & ``That is not what your description does'' \\
4 & Oracle & Where the expected answer comes from, and whether it is independent of the code & ``You graded your own work'' \\
5 & Rule & What the validator mechanically checks & ``Your rule does not test your sentence'' \\
6 & Refusal & Cases the component declines, declared in advance & ``That boundary was drawn to avoid a failure'' \\
7 & Ceiling & The strongest conclusion a pass supports & ``You are carrying this further than it goes'' \\
\bottomrule
\end{tabular}
\end{center}

The fourth column is the point. An ordinary test returns a verdict; this returns
a verdict plus the address of every place the verdict could be wrong. A reader
who doubts a claim does not have to argue with my description of software they
cannot see. They can name a field.

Two consequences follow, and they pull in opposite directions.

The first is that a component can fail in public. That is the property worth
having, and it is why Section~\ref{sec:collection} reports failures rather than
a pass rate. A component that fails is still answerable; a component can be
answerable and trivial. Answerability concerns the form a claim takes, not its
truth and not its importance.

The second is that the ceiling is written by the same person as the claim. A
declared limit is not an independent check; it is a promise about how to read a
result, made by the party with an interest in how it is read. Its value is that
it is specific and public, so a reader can hold a later sentence against it.
Section~\ref{sec:audit} tests whether the ceilings in this collection actually
catch the overreach they exist to catch.

\paragraph{Refusals.} A refusal is informative only when declared in advance and
distinguishable from a breakdown. Components depending on an external tool ---
the Lean proof checker, say --- are required to record a refusal with a stated
limit when the tool is absent, rather than reporting success.
Section~\ref{sec:collection} measures how often that requirement is met, and
finds it is not universal. One honesty condition cannot be discharged from
inside the repository at all: the record shows each boundary as declared at the
audited commit, and cannot show whether it was drawn before or after an awkward
case was met (L6).

\paragraph{The shape is not specific to software.} The record needs a claim in
words, a determinate public case, a procedure a stranger can cause to run, an
observable result, a rule connecting result to claim, a declared boundary, and a
stated ceiling. That the case here is a file of numbers and the procedure a
command is a convenience. A laboratory protocol with declared rejection
conditions, or a sealed evaluation service with published scoring rules, could
satisfy the same shape. I make no claim about those settings.

\section{One claim, end to end}
\label{sec:run}

The component \component{batch8_audio_level_rms_port} computes a loudness level
from short arrays of audio samples. I chose it because it is ordinary: it needs
only a square root, and every part of its evidence fits on one page.

The reported origin is that the private system contains a small macOS recording
application whose \component{AudioLevelMonitor.swift} reduces a stretch of audio
samples to a level between zero and one; the public component re-expresses that
calculation in Python. A stranger cannot open that file, so the name is a report,
not evidence (L1).

It is worse than that, and Section~\ref{sec:audit} is where I found out. The
component carries a check whose job is to confirm the copied source against
declared anchors. It reports success. It is comparing nothing, because the Swift
file was withheld at release and the manifest it iterates over is empty. Read
this section for what it is: a calculation a reader can verify by hand, attached
to a provenance claim whose verification is hollow. Both halves are true at once,
and only one of them is worth anything.

The declared calculation: square each sample, average the squares, take the
square root, multiply by eight, and cap at one. Sixteen-bit integer samples are
first divided by 32{,}767. An empty input gives zero. An unrecognised format is
refused rather than guessed at.

\section{Claim against rule}
\label{sec:audit}

Section~\ref{sec:record} promised that separating the claim from the rule makes
the gap between them findable. This section tests that promise by looking for
the gap, in my own work, across the whole registry.

\paragraph{The method was fixed before the result.} The protocol is committed as
\component{paper/audit_protocol.md} at commit \code{6b21d412}, before any
component was coded. It fixes the population, the verdict vocabulary, the
evidence each verdict must carry, and --- the part that matters most --- the
conditions under which the paper's own central mechanism would count as having
failed. Those conditions were written down so that the result could not be
reinterpreted after it arrived. A reader who suspects the protocol was tuned to
the answer can check its commit against the commit of the results file.

For each component, three texts are compared: the public prose a reader meets
without opening the code; the component's declared ceiling; and what the
validator's check functions actually compute, established by reading them rather
than by reading their names. That last discipline is not incidental. A function
called \code{\_hotkey\_audio\_meter\_contract} that returns a field named
\code{hotkey\_requires\_control\_option\_command\_m} is asserting a behavioural
property in its own vocabulary; whether it establishes one is a separate question
that only the body answers.

\paragraph{Verdicts.} Every component receives exactly one.

Three things in that table deserve to be read slowly.

\subsection{The majority hold}

\auditmatch{} of \componentcount{} components enforce what they describe. That
is the honest headline and it should be stated before the failures, because an
audit that only reports its bad news is not an audit either. Several components
do substantially more than their descriptions suggest: two are coded \emph{rule
exceeds claim}, where the registry's own text calls a check a consistency fold
while the code recomputes a verdict from independent fields and flags
disagreement. Components that invoke real external tools --- a Lean build, a
Swift compile, a statistics library --- generally do what they say, because
invoking a tool is difficult to fake.

\subsection{The failure the design exists to find}

\auditabove{} components describe more than they enforce. The most instructive is
the one this paper chose as its own worked example.

\paragraph{A check that passes by checking nothing.}
Section~\ref{sec:run} presents \component{batch8_audio_level_rms_port} and says
that its code and receipts name the private file it claims to re-express. The
audit asked what enforces that. The answer is a source-manifest check, and here
is what it reports when run:

\begin{Verbatim}[fontsize=\small]
source_module_manifest.module_count                  = 0
source_module_manifest.all_required_anchors_present  = True
source_module_manifest.all_expected_digests_matched  = True
source_module_manifest.status                        = pass
\end{Verbatim}

Every required anchor is present, and every expected digest matches, across zero
modules. The shipped manifest at
\component{examples/batch8_audio_level_rms_port/.../source_module_manifest.json}
carries \code{module\_count: 0} and \code{modules: []}, because
\component{AudioLevelMonitor.swift} was moved into
\code{release\_substitution\_omissions} as a public-safe stub during release: it
is a restricted private source reference and could not be published. The
verification loop then iterates over an empty list. In Python, \code{all([])} is
\code{True}. Among the four anchors it would have compared, had there been
anything to compare them against, is the string
\code{"return min(max(rms * 8, 0), 1)"} --- the formula
Section~\ref{sec:run} walks through.

Nothing here is a lie, and nothing was hidden: the omission is recorded in the
manifest, and the paper already says that a private filename is a report rather
than evidence (L1). What the paper did not say, because I did not know it, is
that the mechanism which would have made the copy checkable reports success while
checking nothing. A vacuous pass and a real pass are indistinguishable in the
output, and the vacuous one is the flagship.

The calculation itself holds up. The audit confirmed, by reading the code and
recomputing by hand, that \component{normalized\_level} really implements the
formula, that the validator genuinely recomputes each reference case and compares
it against the fixture's expected value at a tolerance of $10^{-9}$, and that the
\code{pcm24} refusal is a real refusal raised before any other branch. The
arithmetic a reader is invited to check in Section~\ref{sec:run} is exactly as
sound as it appears. It is the provenance half of the same component that is
hollow --- and the provenance half is the half that connects the public
repository to the private system this paper is nominally about.

\paragraph{A check that tests text instead of behaviour.} The second case is
\component{batch7_demo_take_console_capsule}, and it is worth setting out in full
because every part of it is checkable.

Its public description says it checks ``SwiftPM build-witness posture,
recording-state control, capture-helper bridge contracts, recorder-store capture
FSM boundaries, hotkey/audio-meter \emph{behavior}, and transcribe-payload
construction''. One of those six is a genuine external-tool witness: it runs
\code{swift build} and uses the result. The other five read Swift files as plain
text and test whether fixed strings occur in them. The hotkey and audio-meter
check, at
\component{src/microcosm_core/organs/batch7_demo_take_console_capsule.py:765},
is:

\begin{Verbatim}[fontsize=\small]
hotkey_guard = all(
    token in hotkey
    for token in (
        "static let defaultKey: UInt16 = 46",
        "guard event.keyCode == HotkeyMonitor.defaultKey else { return false }",
        ...
    )
)
\end{Verbatim}

No Swift is compiled or executed. Two separating cases follow immediately, and
both are decisive. A behaviour-preserving rewrite of the Swift --- renamed
variables, refactored control flow, identical behaviour --- would \emph{fail}
this check. And the check would still \emph{pass} if the entire logic body were
deleted and only a comment containing those strings remained, because
\code{token in hotkey} searches the whole file. The rule therefore tests neither
direction of the property its prose names. It tests that a file has not been
edited.

There is a detail here I did not expect to find. Among the strings this check
requires is \code{"return min(max(rms * 8, 0), 1)"} --- the formula of the audio
calculation that Section~\ref{sec:run} walks through as the paper's worked
example. The Swift original of the paper's flagship claim is ``verified'' by
checking that a string containing its formula appears somewhere in a file.

The remaining \auditaboveother{} follow the same two shapes at different
distances. A prose verb implying enforcement --- ``refuses'', ``proves'', ``must
still point to receipts'' --- is resolved by a check on names, on a fixed key
list, or on the presence of a reference rather than on what it refers to. One
component's prose promises that no real proof text can reach a lemma table; the
enforcement is a denylist of four field names, so proof text under a fifth name
passes. Another promises that a declared route ``must still point to receipts'';
the check counts non-empty unique strings and never resolves one. A third shares
the empty-manifest problem above, and there it is load-bearing rather than
incidental: the copied body is a stub, the loader silently falls back to an
in-file reimplementation, and the receipt still advertises the private file as
its source route.

\subsection{The mechanism does not do the job I claimed for it}

The protocol declared, before the audit ran, that if \emph{claim above rule} were
common while \emph{ceiling repairs claim} were rare, the ceiling field would not
be catching overreach and the mechanism would not work as advertised.

That is what the data show. \auditabove{} components claim above their rule;
\auditceiling{} have a ceiling that states the narrower truth. The ceiling field
--- the seventh part of the record, the part this paper argues is what makes the
unit worth having --- catches a small minority of the cases it exists to catch.

The reason is visible in the cases, and it is worse than a drafting lapse.
Ceilings in this collection are written about the \emph{subject}, not about the
\emph{check}. The ceiling above reads ``verified non-secret macro body import
only, not app launch, screen or microphone capture authority, model dispatch,
source mutation, complete UI coverage, release, or publication''. Every clause is
true and none says the thing a reader needs, which is that this check does not
execute anything. The field disciplines what the software is claimed to do and
leaves undisciplined what the evidence is claimed to be.

Two counts show that this is systematic rather than occasional. Three ceiling
templates account for 56 of the \componentcount{} components, so the field is
largely boilerplate. And of the 21 components sharing that one identical ceiling
sentence, 11 were coded as matching their claim, 8 as claiming above it, and 2 as
repaired by it. The same text sits above components that overreach and components
that do not. A field that reads identically on both sides of the distinction it
exists to mark is not marking it.

That is a real defect in the design this paper proposes, found by the procedure
this paper proposes, and it is reported here rather than repaired quietly before
publication. The repair is not difficult to state --- a ceiling should be
required to name the weakest property the check actually establishes, not only
the capabilities the subject lacks --- but stating a repair is not performing
one, and at the audited version it has not been performed.

\subsection{What this audit does not establish}

The audit is mine (L6). I wrote the components, the prose, the ceilings, the
protocol, and the list of things a protocol should look for. It can find
overreach; it cannot show that it found all of it, and its blind spots are my
blind spots twice over.

Coding is judgement, not measurement, and the audit's own check on itself says so
loudly. A reconciliation pass took the three \emph{claim above rule} verdicts
carried at the highest confidence and tried to overturn them by re-reading the
cited code. It overturned two. In one, a hardcoded pass value was real but the
verdict it appeared to decide was in fact gated by a second consumer further
down, which a live run confirmed. That is a 2-in-3 overturn rate on a
deliberately adversarial recheck of the strongest findings.

\auditabove{} is therefore an upper bound, not a measurement, and a reader should
treat it as the number of places worth looking rather than the number of defects.
The direction of the correction is worth noting too: the error was
over-detection, which is the direction an author auditing his own work is least
likely to be accused of and most likely to commit when trying not to flinch.
There was one coding pass and no second independent coder, so there is no
disagreement rate for the other 85. Per-component evidence --- quoted prose,
quoted ceiling, deciding lines, separating case --- is published in
\component{paper/audit_claim_against_check.json} so a disagreement can be pointed
at a specific line rather than at the total.

A verdict concerns the fit between description and rule, not correctness. A
component coded \emph{rule matches claim} may still compute the wrong answer
(L2). And nothing here bears on the private system (L1, L4).

\section{Why the gaps are structural}
\label{sec:gaps}

The seven limits are not an inventory of things I have not got round to. Each
names the same shape of mistake: an observation invites a conclusion, and the
step between them needs an assumption the observation cannot supply. Naming the
assumption is the whole of what this section does, because an assumption with a
name can be argued with, priced, or deliberately accepted, and an unnamed one is
crossed without noticing.

For \textbf{L1} the missing assumption is that the public object came from the
private one, and only a commitment published before the fact, or a reviewer
allowed to see both sides, could supply it. For \textbf{L2} it is that the
expected answer was right, which needs an answer derived without passing through
my code. For \textbf{L3} it is that the rule tests the claim as written --- the
one assumption in this list that a reader can check without leaving the
repository, which is why Section~\ref{sec:audit} could attack it and the others
had to be left standing. For \textbf{L4} it is that chosen cases stand for
unchosen ones, which needs cases selected by someone else after the version is
pinned. For \textbf{L5} it is that the scan covered the relevant risks, which
needs a threat-led review by someone who did not write the scan. For \textbf{L6}
it is that the recorder had no reason to shape the record, and nothing supplies
that except a consequential choice leaving my hands.

\textbf{L7} is the exception, and it is worth stating separately because it is
the one with no remedy at all. \componentcount{} components passing is not
\componentcount{} confirmations; it is one witness counted \componentcount{}
times. No further work of mine changes that, and the temptation to read an
inventory as a score is the failure this paper is most at risk of committing
itself.

Fingerprints are worth a sentence here because they look like origin evidence
and are not. Each copied file carries a SHA-256 value computed from its contents
\cite{nistfips1804}. The National Institute of Standards and Technology (NIST)
expects an approved hash function to make it computationally infeasible to start
from a given file and find a different one with the same value --- second-preimage
resistance, which is a stronger requirement than collision resistance, where an
attacker may choose both files freely
\cite[security-strength table]{nisthashfunctions}. So a match does support a
narrow claim: the public file agrees with the version recorded for it. But I
control both the file and the record, so the agreement is internal consistency,
not provenance (L1).

Two things follow. Almost every remedy above is another person. That is not
modesty but the structure of the problem: a self-published collection can make
its claims addressable and can measure itself against its own standard, as
Sections~\ref{sec:collection} and~\ref{sec:audit} do, and it cannot manufacture
independence at any volume.

And making disagreement local can displace the larger question. A reader can
settle an argument about one input while leaving untouched whether the selection
is fair or the whole is sound. An objection about selection is not answered by
the successful execution of any number of selected items. The registry hosts the
small arguments; it does not settle the large ones.

\section{Related work}
\label{sec:related}

This paper claims no new theory of assurance, testing, or reproducibility. The
ingredients are old; the combination, and its application to a system that
cannot be opened, is what is offered.

\paragraph{Reproducibility and research materials.} Under the National Academies'
convention, computational reproducibility means obtaining consistent results
using the same inputs, steps, methods, code, and conditions; such consistency
does not establish correctness \cite[conclusion 3-1]{nasem2019}. The record here
supplies the materials such a test needs and separates the two properties by
construction: repeatability is the verdict, correctness is a claim about the
oracle field. The Association for Computing Machinery (ACM) calls such research
materials \emph{artifacts}; its badges certify documentation, completeness, and
independent reproduction of results \cite{acmartifact}; Plectis holds neither,
and Appendix~\ref{sec:standards} states its status against each.

\paragraph{Test oracles.} Deciding whether an observed output is correct is the
test oracle problem \cite[p.~507]{barr2015}. The oracle field is a small,
practical response: rather than solve it, name who solved it for each claim. The
same problem is now familiar in machine-learning evaluation under other names
--- benchmark contamination, and models graded by models. A benchmark score is a
claim whose oracle, refusal behaviour, and ceiling are usually unstated; this
collection is a small, fully worked instance of attaching all three to every
claim. I make no claim that the practice scales to a benchmark of consequence.

\paragraph{Selection.} That a curated collection over-represents favourable
cases is analogous to the file-drawer problem, in which studies with null results
go unpublished and the visible literature is consequently unrepresentative
\cite{rosenthal1979}. The analogue here is sharper than usual because the pool is
not merely unpublished but unpublishable, and Section~\ref{sec:collection} finds
the same shape one level up, in which parts of the collection sit outside the
verification floor.

\paragraph{Evaluating what cannot be opened.} Assurance cases link a claim to
argument and evidence; the Object Management Group's metamodel describes them as
auditable claims, arguments, and evidence
\cite[secs.~1.1, 2.2; Annex A.2]{omgsacm2023}. A validator result is not such an
argument, and this work is not an implementation of that standard. NASA defines
independence for verification and validation through technical, managerial, and
financial separation \cite[\S4.4.1.2]{nasa8739}; Plectis has none of the three.
The closest live practice is confidential third-party evaluation of systems the
evaluator cannot fully open, as in externally run assessments of frontier models,
work on controlling untrusted AI systems, and sabotage and scheming evaluations.
This work is deliberately narrower than any of those programmes. It evaluates no
model and no deployment. Its subject is a small collection of software claims,
and its contribution is the record each claim carries.

Section~\ref{sec:audit} is the one place where this paper stops proposing and
starts measuring, and it is worth being exact about what an outsider would add to
it. The audit was run by the author, against a protocol the author wrote, looking
for faults the author thought to look for. An evaluator-run version would change
three things: the coding would not be done by the party whose prose is being
coded; a second coder would give a disagreement rate, which this audit does not
have; and the protocol's blind spots would be someone else's blind spots. The
finding that the ceiling field under-performs its own declared standard is
evidence I did not want and did not expect, which is some protection against the
obvious objection, but it is not independence.

\paragraph{How the record should age.} Repairs should add facts, not erase them.
The appendix keeps failures at the pinned version although later commits repair
some of them. If criticism shows a rule too weak or a claim too broad, the
revision's date and cause are recorded rather than the project appearing always
to have meant the narrower claim. A test rewritten after its outcome is known is
a different test and may be better; the known case shows whether the same failure
returns, but fresh confirmation needs cases whose answers were not used to design
the repair. Disappointment is in scope: if an evaluation finds a component
trivial or no better than a short ordinary script, that belongs on the record
with the same standing as a pass.

\section{Conclusion}
\label{sec:conclusion}

When a system cannot be opened, the useful unit of public evidence is not a
passing test but a claim shipped with a written, checkable statement of its own
ceiling. This paper specified that unit, implemented it across \componentcount{}
components, and audited them against it.

The audit found what the design exists to make findable, in the author's own
work: components whose descriptions promise more than their rules enforce,
including one where prose promising to check behaviour is a search for fixed
strings in a file that is never executed. It also found that the ceiling field,
the mechanism meant to catch exactly this, caught it in a minority of cases ---
a result declared as a falsification condition before the audit ran.

What a reader should take from this is not that the collection is sound. It is
that a claim carrying its own oracle, refusal boundary, and ceiling can be
checked against itself, by anyone, with a published command, and that doing so
here produced findings unfavourable to the author. What a reader must not take
from it is any conclusion about the private system, whose quality remains exactly
as unestablished as it was on the first page.

\section{A first review: check one claim, then break it}

Ten minutes, a terminal, and Python. This is the shortest path from reading the

Clone and pin the version, then run the worked example exactly as
Section~\ref{sec:run} gives it. Do not run the command the repository's own
guidance suggests first: it writes to the saved receipt paths. The paper's
command writes only to \code{/tmp} and leaves the checkout unchanged.

The stored reference for the table is
\component{batch8_audio_level_rms_port_validation_receipt.json}, under
\component{receipts/first_wave/batch8_audio_level_rms_port/}, so a fresh run is
compared against a fixed record rather than against memory.
Under \component{/tmp/plectis-audio-rms/}, open

\section{Names, authorship, and generative AI use}
\label{sec:authorship}

I built the private system over about ten months by directing coding agents based on
artificial intelligence (AI): software tools that edit, run, and revise code
across a task. I set objectives
and review criteria, accepted or rejected output, and sent failures back for
revision. The agents wrote nearly all of the code; I wrote nearly none of it. No
other person worked on the system. At the time of the work I was 22, an
economics undergraduate, working independently and without external funding.

This manuscript was produced the same way. An agentic workflow drafted and
revised the prose from objectives, evidence, and review criteria I supplied; I
selected the claims, required revisions, reviewed and approved the published
version, and am responsible for it. Agents are production tools, not authors.

Two consequences bear on the evidence, and only two.

The first is that an implementation and the program that checks it can share a
mistake when one process drafts both. This is not speculative here:
Section~\ref{sec:audit} found \auditabove{} components whose description and
whose rule disagree, and both were produced by the same process. That is the
concrete form the risk takes in this collection.

The second is that the limit on what a public run can establish would be
identical if every line had been written by hand. Authorship changes how often a
failure occurs, not what a passing test proves. This paper compares no
development methods and estimates no error rates.
