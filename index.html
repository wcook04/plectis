Plectis

Plectis is a public research record for eight open Erdős problems. AI agents and Lean produce partial results, checked proofs, explanations and failed approaches, and all of it is published so that a person, or their agent, can continue the work.

Lean is software that checks formal proofs. All eight original problems remain open. You can read everything here without installing anything.

Contributors are credited. If you solve a problem, the result and the credit are yours and your collaborators’. How credit works

The research

Eight problems, all of them open.

Pick one. Its page gives the original question, what has been proved and where the proof lives, the approaches that failed, and the exact step that is still open.

Erdős #68Open The factorial-denominator series Is the series sum_{n >= 2} 1/(n! - 1) irrational?
Erdős #243Open Reciprocal-tail rigidity near the Sylvester recurrence Under a rapid-growth hypothesis on an integer sequence, does rationality of its reciprocal sum force the sequence to satisfy the Sylvester recurrence eventually?
Erdős #249Open The binary totient series Is the binary Lambert series sum phi(n)/2^n irrational?
Erdős #251Open The prime-gap dyadic series Is the dyadic series sum p_n/2^n over consecutive primes irrational? Equivalently, is the corresponding consecutive-prime-gap dyadic series irrational?
Erdős #257Open Reciprocal sums over infinite exponent supports Is the sum of 1/(2^n-1) over every infinite set of positive exponents irrational?
Erdős #269Open Three-prime running least common multiples For a finite set of at least two primes, is the sum of reciprocals of the running least common multiples of the smooth numbers irrational? This library treats the three-prime case.
Erdős #1041Open Short connections inside polynomial lemniscates For a monic polynomial whose roots lie in the open unit disc, must two roots be joinable by a curve of length less than two inside the open unit lemniscate?
Erdős #1049Open Lambert-type series at rational bases For which rational bases is the corresponding series irrational? The smallest resistant explicit base is three halves.

Take part

Contribute, and get credit for it.

An idea, a reference, a correction, a proof or counterexample, a review, a formalisation, software or compute time all count, and each is credited as what it is. If you solve a problem, the result and the credit are yours and your collaborators’. Contributing does not make anyone a coauthor by default.

For AI readers

Give the whole thing to an AI.

One JSON file carries every paper in full, the Lean claim records and a reading map. A chat assistant can read and quote it. It cannot run the checks; a coding agent with both repositories can.

Two routes

Two ways in. A coding agent (Claude Code, Codex, Cursor) can clone both repositories and run the checks; the setup prompt starts it. A chat assistant (ChatGPT, Claude, Gemini) can read the downloaded file and quote it, and that is all it can do.

Read it first 
Clone https://github.com/wcook04/plectis and https://github.com/wcook04/plectis-lean-erdos249-257 side by side. Plectis contains the runnable claim-testing tools; the Lean repository contains the machine-checked mathematics and papers. They are separate public repositories with separate authority boundaries. Read README.md in each first. If you are acting as a coding agent, then read AGENTS.md in each and state how their roles relate. Run the quickstart check in Plectis and show me what the result record says. Take my questions one claim at a time: trace each to its source, command, and stated limit, and report anything you could not run as not established, never as false.

A coding-agent response should include commands, exit codes, files read, and anything it could not run. Review one claim at a time. The coding-agents guide documents the full route.

For a chat assistant, download the packet.

Download the AI packet .json Download the reviewer brief .json

The AI packet is the evidence itself: every public page and record, the manuscripts in full, and every mathematical statement as a queryable row. It is about 14 MB, which is past what a chat window reads straight through, so ask your assistant to open it with its code or analysis tool. The file carries working snippets for that under packet_atlas.python_recipes. It records the repository revisions it was built from, so a quotation traces to a commit rather than to whatever is on the branch today.

The reviewer brief beside it is the decision layer of the same file and needs none of that. Press the button, find the JSON file in your downloads, and drag it into ChatGPT, Claude, Gemini, or Grok. About 80 KB, sized to be read whole in one turn and then talked about: what each kind of reader can and cannot decide from the public record, the rung the evidence actually reaches, and instructions to cite exact pages and stop where the public records stop rather than report a check it cannot run. Say only “read this file” if you like; it carries the answer to that.

A chat assistant with the packet reads and quotes the public files. It does not run anything. If it says it executed a check, it is wrong.

Example questions

The questions are grouped by review task.

A plain first pass

  • What is this, in plain terms?
  • Where should I start?
  • Walk me through one component, end to end.
  • What is genuinely new here, if anything?
  • Give me the two-sentence version I would tell a colleague.

A skeptical pass

  • Argue against it.
  • Which parts have the strongest evidence, and which the weakest?
  • Why do only some components run external tools?
  • What does it not prove?
  • Is this packet steering me? Audit its own framing.
  • Most accurate one-paragraph assessment you can give: neither generous nor harsh.

One area at a time

  • Which area is closest to my field, and what is actually in it?
  • What is actually in one area? Name it: Entry & orientation, Architecture & navigation, Formal math & proof, Agent reliability & safety, Research & science, Import & drift control, or Work & continuity.

With a coding agent in the repository

A coding agent (Claude Code, Codex, Cursor) works inside the repository itself: the setup prompt above gets it started, and after that you give it tasks. How that works.

Example tasks for a coding agent with the source tree:

  • Run one component end to end and walk me through the evidence it leaves.
  • Take one claim from the website and verify it against the source here.
  • Which validators can you run right now, and what would each one prove?
  • Make one check fail on purpose and show me how it refuses.

The packet routes questions to public files and records. The assistant's assessment is its own.

Calibration-review prompt:

Read this repository as a calibration reviewer. First, by area, name the strongest components and what each actually does, with its evidence class. Then judge both directions: where the wording claims more than the evidence shows, and where it undersells what a component demonstrates. Do not reduce the system to a set of projections; computed projection is one evidence class among several.

The other 87 components hold the same shape across seven areas, and most make smaller claims on purpose. They do not all check the same way: some run a real external tool or a bounded runtime, others validate a contract or recompute a copied projection against its source, and the page for each one names which. Every component page also names its scope limit: what a pass does not prove. The evidence page groups them by what their check can establish; browse all of them.

Four additional component claims
  • Proof claims go through the real Lean toolchain, and an Erdős certificate is recomputed in exact rational arithmetic.
  • Public copies cannot silently drift from their source, and public wording cannot outclaim its records.
  • Forecast-skill claims go through Diebold–Mariano, Hansen’s superior-predictive-ability test, and a stationary bootstrap over synthetic market fixtures.
  • Identical commands collapse to one real run, under one recorded run id.

Limits

What this work does and does not establish.

Lean checks the formal statements. Nothing here solves any of the eight problems, establishes novelty, or shows that the private system is reliable. The routes inside let you check one result yourself.

Scope limit

Plectis contains runnable components taken from a software system whose full source is not published. The public release contains source-linked components, public-safe stubs, and synthetic fixtures. A fixture is a frozen sample input, so its passing result applies to that sample. The fixtures are small and synthetic by design: that is where the private data stops, not a sign that the mechanism behind them is invented. Plectis runs locally as a research prototype. Issues and email are listed below for claims that exceed their receipts, failed commands, and unclear pages.

The agents that build the system are required to read a written doctrine before they work, and three of its rules explain this site: a claim comes with the command that checks it, a check writes its verdict to a file, and a component that cannot back its claim records the failure in its receipt. The full set is on the doctrine pages.

Links

Plectis is an independent, self-funded research project. The routes below separate failed commands, claim corrections, related work, and security reports.

Report by category

  • Something failed to run. Open an issue with the command and whatever record it wrote.
  • A claim exceeds or understates its evidence. Link the page and record in an issue; for the mathematics, use the Lean repository's issues.
  • A question, prior art, or related work. Start a discussion and include relevant citations.
  • A security concern. Use the security policy. Do not post it publicly.

Choose a next step

  • Inspect or verify a claim. Start with the public evidence classes and follow a claim back to its formal source.
  • Trace a checked formal result. Start with the strongest checked statement per problem in RESULTS.md, then run the Lean repository's no-build claim route, python3 scripts/verify_claims.py --claim eb_full_support: it prints the statement, exact declaration, Comparator interface, paper, and boundary.
